## 1. Резиме и оценка

**Оценка: ПРИФАТЛИВО СО ЗАБЕЛЕШКИ.**

- **Нема критични безбедносни дупки** во ревидираните рути. Расчистена е сомнежот за mass-assignment: сите PATCH рути користат **експлицитни field whitelist-и**, нема `.passthrough()` во `web/app/api`.
- **Batch 4 вердикт: позитивен** — рефакторирањето (whitelist-и, `requireLabelGroupAccess` defense-in-depth, RBAC на `users` рутата, аудит-запис) значително ја зацврсти конзистентноста. Остануваат **2 високи, таргетирани наоди** (В-1, В-2) кои не бараат редизајн туку мали, приоритетни поправки.

## 4. Наоди по приоритет

### 4.1 Висок

**В-1 — 500-грешки протекуваат внатрешен `message` до клиентот**

- **Локација:** `web/lib/api/auth-guard.ts:35-43` (`apiErrorResponse`)
- **Доказ:** `const msg = err instanceof Error ? err.message : 'Internal server error'` — при `status >= 500` оригиналниот `err.message` (Supabase/DB детали, SQL фрагменти, внатрешни патеки) се враќа во HTTP-одговорот. Датотеката се користи од 23 рута-фајлови.
- **Влијание:** информациско протекување кон овластени и неовластени клиенти; им помага на напаѓачите да го мапираат внатрешниот систем.
- **Препорака:** за `status >= 500` секогаш враќај го генеричкиот `„Internal server error"`; целосниот `message` само во логовите (веќе има `captureException` во истиот хелпер).
- **Столб/принцип:** P0 (Фундамент) · **P-05** (безбедноста не е преговарачка).

**В-2 — Нулта тест покриеност на безбедносните хелпери**

- **Локација:** `web/lib/api/` — `requireAuth` (68 повикувачи), `parseJsonBody` (31), `validateBody` (15), `apiErrorResponse` (68), `requireProjectAccess` (33), `requireProjectMutate` (24)
- **Доказ:** единствениот тестиран хелпер е `filterAllowedFields` (`web/lib/api/__tests__/field-whitelists.test.ts`); ниту еден од шесте критични хелпери нема покривачки тест.
- **Влијание:** овие се chokepoint-ови на целата авторизација и валидација — регресија тука значи регресија насекаде, без безбедносна мрежа во CI.
- **Препорака:** приоритетни unit тестови за `apiErrorResponse` и `requireAuth` (го покриваат истиот фајл, мал труд — висок поврат), па потоа за `parseJsonBody`/`validateBody` според веќе постоечкиот шаблон во `field-whitelists.test.ts`.
- **Столб/принцип:** P0 (Фундамент) · **P-05** + **P-06** (една конвенција, еден систем) · метрика на успех од столбот („тестови за секој критичен тек").

### 4.2 Среден

**С-1 — Дуална валидација: `parseJsonBody` (24+ рути) vs `validateBody` (6 рути)**

- **Доказ:** два паралелни механизми за валидација; `report` рутата враќа неконзистентен error облик. Потврдено и во STRATEGY-v2.1 §6.2.
- **Препорака:** мигрирај ги сите рути на единствениот `validateBody` + заеднички `{ data, error }` облик (Фаза 0).
- **Столб/принцип:** P0 · **P-06**.

**С-2 — Дуален PDF pipeline + stale README**

- **Доказ:** `web/lib/pdf/generator.ts` (pdfkit, 294 линии, i18n mk/en/de/sl/sr) е во употреба преку `web/app/api/report/route.ts` и има тест; `packages/photo-report-pdf/` (Python/reportlab, со сопствен тест, `pyproject.toml`, `publish.yml`) е напуштен. Покрај тоа, главниот `README.md` вели „PDF Извештаи: Python пакет" — **противречи** на кодот што web-апликацијата всушност го користи.
- **Влијание:** две имплементации со различно однесување; читачот на репото (нов developer, клиент) добива погрешна слика за архитектурата.
- **Препорака:** избриши го python пакетот (класифициран како ❌ кој крши P-06 во STRATEGY-v2.1 §5.2 и §6.2) и ажурирај го README; или — ако пакетот има жива употреба — формално интегрирај го и отстрани ја TS имплементацијата.
- **Столб/принцип:** P0 · **P-06** (еден PDF pipeline).

**С-3 — CSP со `'unsafe-inline' 'unsafe-eval'`**

- **Доказ:** `web/next.config.ts` — CSP дозволува `unsafe-inline` и `unsafe-eval`, што го разводнува заштитниот ефект на CSP против XSS. Потврдено во §6.2.
- **Препорака:** зацврсти го CSP без да ја скршиш апликацијата (нека се потврди со реално сурфање по сите екрани).
- **Столб/принцип:** P0 · **P-05**.

**С-4 — Нема PWA капацитет (без manifest/Service Worker)**

- **Доказ:** `web/public/` содржи само фонтови + стандардни Next.js SVGs; глобалната претрага не најде `manifest`, `sw.js` или `service-worker` никаде во `web/`.
- **Влијание:** платформата е декларирана mobile-first, но нема инсталабилност ниту офлајн-капацитет.
- **Препорака:** додај PWA manifest + минимален Service Worker. Веќе е **прифатено** во столбот (§5.2: „PWA manifest + Service Worker → ✅ Прифатено (Фаза 0)"; §7 Фаза 0) и го решава конфликтот „Native рано" од STRATEGY-v2.0 §6.1 преку принципот **P-08** (Web/PWA прво; native само кога ќе се плати).
- **Столб/принцип:** P0+P1 · **P-03** (офлајн = работи секаде) + **P-08**.

### 4.3 Низок

**Н-1 — Голема површина на RLS политики**

- **Доказ:** **135 RLS политики низ 28 миграциски фајлови** (најмногу: `20260731000001_fix_cross_tenant_rls.sql` — 19, `20260730000001_create_labels.sql` — 15, `20260725000014_fix_rls_recursion.sql` — 14; плус наменска `20260729000001_storage_security.sql`).
- **Влијание:** не е пропуст — напротив, хардненингот е сериозен. Но секоја идна миграција мора да се проверува против целиот сет (ризик од регресија при нови политики).
- **Препорака:** при секоја нова RLS миграција во SPEC-от декларирај „влијае на N постоечки политики" (дел од TEMPLATE портата); месечен аудит-чек.
- **Столб/принцип:** P0 · **P-05**.

**Н-2 — Фрагментирана „вистина за денот" (timezone)**

- **Доказ:** 3 начини на day-bucketing според §6.2; нема единствен детерминистички day-key (проектна временска зона).
- **Препорака:** единствен timezone-модел — веќе специфициран во `SPEC-risk-roadmap.md` Фаза 1; имплементирај во Фаза 0.
- **Столб/принцип:** P0 · **P-02** (временска врзаност).

**Н-3 — Локални артефакти во python пакетот**

- **Доказ:** `packages/photo-report-pdf/` содржи локални `.venv`/`.mypy_cache`/`.pytest_cache`/`.ruff_cache` (не се во git — добро; пакетот нема сопствен `.gitignore`).
- **Препорака:** пакетот е кандидат за бришење поради С-2; ако остане, додај `.gitignore` во пакетот.
- **Столб/принцип:** P0 · **P-06**.

1. **В-1:** во `apiErrorResponse` (`auth-guard.ts:41`) — за `status >= 500` врати генерички „Internal server error", целосниот message само во лог. *(една линија, елиминира информациско протекување)*

3. **С-2:** избриши го python пакетот + поправи го README (P-06) — елиминира дуален систем и погрешна документација.
4. **С-4:** PWA manifest + минимален SW — веќе прифатено во столбот, Фаза 0.
5. **С-1:** миграција на преостанатите рути на `validateBody` — кон едиствена конвенција.

> **Порта:** секоја од овие поправки треба да помине низ `docs/TEMPLATE-feature-spec.md` (декларирање столб + принцип + метрика).
